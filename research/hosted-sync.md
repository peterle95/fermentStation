# Hosted offline-first sync research

Research for [issue #41](https://github.com/peterle95/fermentstation/issues/41) and [issue #40](https://github.com/peterle95/fermentstation/issues/40), 2026-11-02. Provider limits are current published figures, not a service guarantee; recheck before implementation. Repository code is authoritative over older research and audit recommendations.

## Decision

**Do not promise or enable public hosted sync yet.** Prototype an explicitly opt-in, capped Supabase Free pilot only after durable local storage and export/recovery are verified. Supabase is the best first hosted candidate, not a $0 production guarantee: its shared 1 GB photo allowance is tiny, free projects can pause or be restricted, and production magic-link email needs a separate SMTP provider whose free availability and cost are unresolved. Do not attach a paid plan to make the pilot work. Gate public rollout on a documented, enforceable $0 operating envelope, abuse controls, email delivery, security tests, and evidence that conflicts cannot silently destroy work. If any gate fails, ship local-only plus ZIP; retain Syncthing as an advanced choice.

No account, anonymous session, network call, or hosted project is required for initial single-device use. Hosted sync is an optional mirror, not a backup or the authority over unsynced local edits. Keep domain types and shared-folder JSON unchanged; any mapping and sync metadata live at the platform boundary. One account represents one household in v1; multiple separate accounts/invitations are deferred.

## Evidence

### What the app actually stores

- The present exchange format is **three aggregate files**, not the per-batch file proposal in the older `research/free-sync.md`: `manifest.json`, `records/{shell,profiles,batches}.json`, and `photos/<batch-id>/<timeline-id>.<ext>`. Photos are externalized from data URLs on write and hydrated on read; IDs and existing trash arrays are retained. `docs/shared-data-format.md`; `src/platform/shared-data-store.ts:9-15,194-262`; `src/domain/batches.ts:11-60`.
- Shared-folder storage is canonical when selected, rather than merely a mirror. It checks schema version 1 and an interrupted-write marker; it rejects malformed snapshots and does not load `.sync-conflict-` files, but reports them. Initialization with data on both sides requests an explicit choice and backs up the existing folder before replacement. `src/platform/shared-data-store.ts:55-127,181-227`; `docs/shared-data-format.md:18-22`.
- Audit W9 identifies whole-snapshot rejection of newer schemas and no migration framework; W10 identifies conflict notice without in-app resolution (`outputs/repo-implementation-advisor-report.md:61-62,98-102`). Its pre-user reset suggestion is **not acceptable for real users**. Also, missing shared photos currently invalidate the entire hydrated snapshot; cloud partial uploads/downloads must not turn a partial snapshot into empty state (`shared-data-store.ts:244-262`).
- `src/platform/archive.ts:33-64,67-100` exports profiles, batches, trash and photo bytes with hashes and import collision handling, **not shell settings**; import limits ZIP to 200 MiB compressed / 250 MiB expanded. Verify end-to-end UI/platform availability and limits before describing it as complete backup or recovery for large households. Current Settings says “No data leaves this device” (`src/App.tsx:393`); hosted mode makes that untrue. Issue #40 identifies IndexedDB work in #35/#39 as a prerequisite, not an already delivered guarantee.

### Provider evidence and implications

- [Supabase pricing](https://supabase.com/pricing): Free includes 500 MB database **per project**, 1 GB file storage, 5 GB uncached and 5 GB cached egress, 50,000 monthly active users, two active free projects; storage and most usage quotas are organization-wide, not per household ([billing](https://supabase.com/docs/guides/platform/billing-on-supabase)). Unlimited API requests does not mean unlimited capacity. [Egress](https://supabase.com/docs/guides/platform/manage-your-usage/egress) counts across services; cached and uncached have separate quotas, so do not assume private photo reads are cache hits or add the two as guaranteed 10 GB usable. Free quota excess may trigger notification, grace and restrictions; exact response/timing is not guaranteed ([billing FAQ](https://supabase.com/docs/guides/platform/billing-faq)). Free projects with insufficient database activity over seven days can be paused; restoration is owner-operated with a one-year restore window ([pausing](https://supabase.com/docs/guides/platform/free-project-pausing)). Free pricing lists no automatic backups. This is unsuitable as the only copy.
- [Supabase anonymous auth](https://supabase.com/docs/guides/auth/auth-anonymous) supports linking an email to an anonymous identity, but losing its session before linking loses access to that identity. Anonymous sign-ins are authenticated for RLS, need abuse prevention, and have no automatic cleanup. The documented linking setup requires manual linking enabled; verify email confirmation and pre-existing-email collision behavior in the exact SDK/configuration before relying on it. The default email service sends only to organization team addresses, at two messages/hour project-wide; custom SMTP is needed for ordinary users ([SMTP](https://supabase.com/docs/guides/auth/auth-smtp), [rate limits](https://supabase.com/docs/guides/auth/rate-limits)). Magic links/OTP are one-time and redirect configuration matters ([passwordless auth](https://supabase.com/docs/guides/auth/auth-email-passwordless)). This is a release blocker, not a footnote.
- [Firebase Firestore pricing](https://firebase.google.com/docs/firestore/pricing) offers one free database/project: 1 GiB, 50,000 reads/day, 20,000 writes/day, 20,000 deletes/day and 10 GiB outbound/month; counts and indexes matter. But [Firebase Storage FAQ](https://firebase.google.com/docs/storage/faq-and-troubleshooting) says Cloud Storage requires the pay-as-you-go Blaze plan even for the default bucket. A no-cost usage allowance on Blaze is not a hard $0 cap; photos therefore make Firebase a poor fit under the stated constraint. Check current [Firebase pricing](https://firebase.google.com/pricing/) before reconsidering.
- [Syncthing](https://docs.syncthing.net/users/faq.html) exchanges files between online peers and is not a backup; [conflict handling](https://docs.syncthing.net/users/syncing.html#conflicting-changes) preserves a divergent file as a propagated conflict copy, without semantic merge. It costs no hosted subscription but requires installation, pairing and ongoing device operation; it is appropriate for the maintainer's advanced path, not zero-setup consumer sync.

## Minimum hosted design

### Identity, consent and isolation

1. On explicit “Turn on sync”, explain that records, photos and email will be sent to the operator's Supabase project, identify the provider and retention/deletion policy, and obtain consent. Recommend **email first** for the pilot: confirm ownership, then establish the household. This avoids advertising an anonymous cloud copy as recoverable before a login exists. Optional anonymous-first linking is a later experiment, not a prerequisite for local usage. For second-device attach, sign in to the **same verified account** with email OTP/link, then explicitly preview local versus cloud data; never silently replace either. Email is a shared household credential in v1, not separate member access.
2. If later adding anonymous-first: create it only after opt-in, retain its auth session securely, warn that loss before email linking makes its remote copy inaccessible, and verify linking preserves the user ID. If the email already belongs to another account, do not assume identities merge: retain/export both local datasets, sign in to the existing account separately and require an explicit collision-aware import. Test magic-link/OTP callbacks, redirects and interrupted flows on iOS PWA, Android and Tauri. Public users need verified custom SMTP with an independently confirmed $0 allowance and abuse policy.
3. A household is keyed by the authenticated user's stable UUID. Enable RLS and least-privilege grants for every exposed table; `auth.uid()` must equal the household owner on reads and writes. Use a private photo bucket with matching owner-prefix policies on `storage.objects`; validate bucket and path server-side. Anonymous auth uses the authenticated role, not the unauthenticated `anon` role. Never ship service-role/secret keys in any app. Test cross-user reads, writes, guessed photo paths, RPCs, views and deletion explicitly. [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Storage access](https://supabase.com/docs/guides/storage/security/access-control). RLS is access control, not end-to-end encryption: the operator/provider can access server-side data; disclose this honestly.

### Records, photos and divergence

Use one row per existing aggregate (`shell`, `profiles`, `batches`) per household, with existing JSON as `jsonb`, a schema version, monotonic server revision, and opaque operation ID. Preserve batch/profile/timeline IDs and ordering; no invented per-record timestamps, and no domain-format changes. Current trash and `deletedAt` fields travel inside the payload. A whole aggregate is a conflict unit, so unrelated edits within the same batches file may conflict; this is the deliberate cost of preserving existing shape. Splitting into batch-level rows can follow only with a tested, lossless adapter for ordering, references and trash. Do not claim per-record LWW is already implemented.

Store immutable photo bytes in the private bucket under household plus content hash; replace data URLs at the hosted boundary with a reference, MIME, size and hash, then verify and hydrate before applying. Upload object before publishing a referencing row; download and validate every required object before committing its referencing generation. Missing or corrupt objects keep the last valid local data and show a retryable problem, never an empty snapshot. Object upload and SQL commit are not one transaction: a failed commit can orphan an upload; conservatively retain it until a safe, reference-aware cleanup exists. Concurrent revisions and conflict copies can reference old objects, so never eagerly delete them. Do not promise unlimited photo retention.

Use compare-and-swap against each aggregate's last observed server revision via a narrowly scoped transactional SQL function: check ownership and expected revision, then update and return the new revision atomically. Give each mutation a persisted unique ID; record successful IDs transactionally so a lost response and retry is idempotent. A stale base must return conflict, not overwrite. Keep both immutable local and remote candidate payloads and referenced photos; quarantine candidates rather than loading them as canonical. UI shows which aggregate diverged, offers export of both and explicit keep-local/keep-remote after preview; recheck current revision on resolution and re-conflict if it changed. This is inspired by the existing conflict-copy discipline, not literal Syncthing filename behavior or an automatic merge. Do not silently select a timestamp winner. Until real conflict-resolution UI works, do not ship hosted sync beyond an internal experiment.

Treat moving an item to trash, restoration and permanent deletion as versioned aggregate updates. A stale offline update cannot resurrect a permanent deletion because its base revision fails CAS; do not discard the revision history/floor needed to detect stale clients. Never garbage-collect tombstone metadata just because a device is offline for a fixed period: if metadata is ever compacted, require stale devices to rebootstrap and surface their pending edits as conflicts. Cross-aggregate operations need an atomic multi-row server transaction and an atomic local apply, or a published generation/commit marker that readers validate as a complete set; independent row commits can otherwise create mixed profiles/batches. For v1 prefer a single logical snapshot transaction whenever a change spans aggregates.

### Local-first protocol and schema

- Persist the user edit and outbox entry **atomically** in durable local storage before reporting saved. A background worker is an optimization, not a guarantee: foreground startup/resume and manual retry drain the outbox. If the local persistence layer cannot atomically commit state plus outbox on a platform, hosted sync is blocked there until it can; an in-memory promise queue is not durable. #35/#39 IndexedDB completion and native/Tauri transaction or crash-safe journal verification are prerequisites. Local quota/write failure must be visible; do not claim the edit was saved.
- Persist bases, mutations, photo dependencies and retry state. Upload photos, then CAS rows; acknowledge/remove an outbox entry only after confirmed idempotent server commit and durable local acknowledgment. Fetch changes on launch/resume and explicit refresh, validate complete data and apply only where no unacknowledged divergent work exists. A crash at any step must resume without losing either version. Network offline, 429, auth expiry, storage full, paused project or RLS failure leaves edits local and queued; show pending count, last successful sync and actionable reason, back off with jitter, and never say “synced” prematurely. ZIP export and normal local use must remain available when cloud is down.
- Carry independent sync-protocol and payload schema versions. An unknown newer version is quarantined, not parsed as v1 or overwritten; pause writes, preserve/export local pending data and ask for an app update. For old versions, ship and test explicit one-way migrations with pre-migration export and rollback/recovery; never use the audit's pre-user reset policy on real data. A mixed-version device must not down-convert or write unsupported records. Verify validators and migration across both archive and shared-folder formats (W9).
- Settings copy is conditional: local-only can say data stays on the device **only if other network behavior also supports that claim**; hosted mode names records/photos/email and network transfer. Offer disconnect (stop transfers, retain local data), separate deliberate cloud deletion with confirmation, and export before either. Define deletion of account, records, conflict versions and objects, and disclose provider retention; never equate disconnect with deletion. Advanced shared-folder mode remains hidden by default and mutually exclusive with hosted sync until an explicit, backed-up migration is designed; two independently writable transports must not race.

## Free-tier budget and failure envelope

Illustrative decimal MB/GB, not measurements; 1 GB = 1,000 MB. Assume one shared Supabase project, two devices/household, no prior usage, 50 photos × 2 MB = **100 MB per household**, 2 MB of JSON, and one initial second-device download. Photo objects alone fill 1,000 / 100 = **10 households** at the hard theoretical ceiling; a 70% planning threshold gives **7** before overhead, orphan objects, conflicts or other projects. At 100 households this becomes 10 GB of photos, ten times the allowance. A household adding 10 × 2 MB photos/month adds 20 MB/month: from 100 MB, one household reaches 1 GB after roughly 45 months if alone; 7 households add 140 MB/month, consuming the remaining 300 MB in about 2.1 months. Compression, photo size and actual usage are unknown; measure rather than assume them.

At 2 MB JSON per household, the 500 MB DB headline suggests 250 households before DB indexes, auth, revisions, conflict copies and other overhead; **not a safe entitlement**. Under the sample, one second-device initial download is about 102 MB/household: 5,000 / 102 ≈ 49 households per month if all uncached and no other traffic. Twenty households redownloading 100 MB twice/month consume 4,000 MB of the 5,000 MB uncached allowance before metadata, retries and other services. Cache behavior, upload/download overhead, provider units and real JSON sizes are unknown. 50,000 MAU is an organization-wide ceiling, not 50,000 households or a storage entitlement; linked devices sharing an auth user need not equal separate users. Storage is the likely first bottleneck in this scenario.

Enforce a conservative pilot enrollment cap and per-household byte/photo limits **server-side**, not just client UI; guard concurrent reservations and direct API uploads, request sizes, account creation and polling. Verify Storage policy/transaction enforcement in a hostile-client test: RLS alone does not impose a byte quota, and a DB reservation plus a separate object upload is not automatically atomic. Until a reliable cap exists, use a closed trusted pilot only. Monitor actual DB, object storage, egress, SMTP, auth and errors, alert at 50% and 70%, stop new enrollments/uploads before the reserve is exhausted, and keep downloads/export available as long as the provider permits. If the provider restricts even reads, show outage and preserve local data; do not imply an app-side cap can prevent provider-wide restriction. Never auto-upgrade to paid service. If the $0 SMTP or storage envelope fails, suspend hosted enrollment and fall back to local/ZIP.

## Alternatives

| Approach | Fit | Principal limitation |
| --- | --- | --- |
| Supabase Free + custom SMTP | Best candidate for a controlled hosted pilot; Postgres CAS, RLS and private objects are available | Tiny shared photo pool, ops/security work, SMTP prerequisite, pause/restriction risk; not guaranteed $0 at public scale |
| Firebase Spark Firestore | Offline-capable database candidate for record-only experiments | Cloud Storage requires Blaze; Firestore quotas and document sizes still apply, and database offline behavior does not solve app conflict semantics |
| Syncthing + existing shared folder | Existing advanced household workflow, no hosted account | User setup and peer availability; conflict copies need manual resolution; not backup |
| Local only + ZIP | Default and $0 fallback, no service dependency | Manual transfer, explicit collision handling, archive size limits and shell settings omission; not automatic sync |

## Rollout, validation and fallback

Estimates are rough engineering time for one developer, not commitments; overlap, platform surprises and external SMTP approval can expand them:

1. **Prerequisites, 3–6 days:** land/verify #35/#39, durable atomic outbox on each target, ZIP usability and limitations, photo-failure handling, honest privacy copy, backups and cross-platform crash tests. This is a gate, not work already done.
2. **Internal proof, 5–10 days:** Supabase schema/RLS and private objects; quota enforcement experiment; email/redirect proof; CAS/idempotency/outbox; interrupted upload and two-device tests. No real public data until privacy, deletion and operational ownership are reviewed.
3. **Closed opt-in pilot, 5–10 days:** conflict review, schema fencing, status/repair UI, security/abuse tests, monitoring and capped enrollment. Start with web/PWA for iteration **only after** IndexedDB durability and actual iOS Safari install/eviction/offline tests; add Android then Tauri after native persistence, link callbacks and background/resume verification. This sequence is a recommendation, not evidence that any platform is already supported. Test airplane mode edits, concurrent edits/deletes, duplicate delivery, crash at every commit boundary, quota/full disk, expired auth, provider pause, missing photos and rollback.
4. **Public decision, 2–5 days plus observation:** review measured capacity and support burden, $0 SMTP/abuse safeguards, RLS penetration tests, privacy/retention and restore drills. Estimated total **15–31 engineering days**, excluding external waiting and unknown migration/platform complexity. Public rollout is conditional, not automatic after elapsed time.

**Fallback:** local-only by default; use ZIP export/import with collision review and retain separate independent backups. Users who can manage setup may continue the existing advanced Syncthing shared-folder workflow. Preserve unsynced local data and export paths if the pilot ends; communicate service shutdown and cloud deletion separately. Neither sync method is a substitute for tested backups.
